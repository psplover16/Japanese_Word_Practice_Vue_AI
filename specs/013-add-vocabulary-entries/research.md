# 研究紀錄：單字練習補充詞彙

## 決策 1：`說話` 沿用既有 `話す` 覆蓋，不新增重複詞條

- **決策**: 保留既有 `はなす / 話す / 說話` 資料列作為本次「說話」需求的覆蓋來源。
- **理由**: 字典資料檔已存在 `話す -> 說話`，若再新增另一筆只會製造重複覆蓋，違反本功能的去重要求。
- **考慮過的替代方案**:
  - 新增另一筆 `話す` 或 `言う` 來覆蓋「說話」: 捨棄，因為會造成重複或語意偏移。

## 決策 2：本次新詞條固定採用 `肌`、`滑らか`、`動き`

- **決策**: 依使用者釐清，三個新增詞義的標準日文詞條分別為：
  - `皮膚 -> 肌`
  - `光滑 -> 滑らか`
  - `動作 -> 動き`
- **理由**: 使用者明確要求以詞典基本型收錄，且指出「皮膚」應使用 `肌`；先前又以例句 `動きがなめらか` 指向 `動き` 與 `滑らか` 的實際用法。
- **考慮過的替代方案**:
  - `皮膚 -> 皮膚`: 捨棄，使用者已明確指定 `肌`。
  - `動作 -> 動く`: 捨棄，使用者已確認要用 `動き`。
  - `光滑 -> つるつる` 等口語表現: 捨棄，與已確認詞條不符。

## 決策 3：新資料採僅追加策略，直接追加在 `rawVocabularyEntries` 尾端

- **決策**: 只在 [`src/modules/vocabulary/data/jpWords.ts`](C:/Users/user1/Documents/Japanese_Word_Practice_Vue_AI/src/modules/vocabulary/data/jpWords.ts) 的 `rawVocabularyEntries` 最後面追加新詞條。
- **理由**: 這符合使用者釐清，也能保留既有資料順序與既有 id 穩定性。由於 `normalizeVocabularyEntries()` 以 index 產生 id，僅追加策略能確保 1..1076 不變，只新增 1077..1079。
- **考慮過的替代方案**:
  - 依 stage 插入到中段: 捨棄，會漂移後續所有 id，增加註記與測試回歸風險。
  - 另建 overlay/patch 檔在執行期合併: 捨棄，對 3 筆靜態資料來說複雜度過高。

## 決策 4：stage 佈局採 `肌 -> Stage1`、`滑らか/動き -> Stage2`

- **決策**:
  - `肌` 放入 `Stage1_基礎生活`
  - `滑らか` 放入 `Stage2_日常強化`
  - `動き` 放入 `Stage2_日常強化`
- **理由**:
  - `肌` 屬於身體部位，和既有 `頭`、`足`、`手`、`目`、`耳`、`口` 同類，適合放在 Stage1。
  - `滑らか` 為描述性詞彙，性質更接近 Stage2 既有的 `きれい`、`静か`、`にぎやか`。
  - `動き` 雖與 `動く` 相關，但作為名詞化概念更接近 Stage2 的描述／延伸用語，也與 `滑らか` 在同一句型中搭配自然。
- **考慮過的替代方案**:
  - 三筆全部放 Stage1: 捨棄，會把較描述性的 `滑らか`、`動き` 壓得過於基礎。
  - 將 `動き` 放 Stage5 抽象核心: 捨棄，對本次學習情境過重。

## 決策 5：驗證重點是資料筆數、可搜尋覆蓋與負向範圍，而不是新 UI

- **決策**: 測試優先更新 `vocabularyData.spec.ts`、`VocabularyViewSmoke.spec.ts`、`vocabulary-word-practice.spec.ts`，必要時保留 `RouteOwnership.spec.ts` 原樣作為負向邊界驗證。
- **理由**: 本功能不新增 UI 或新互動，主要風險集中在資料筆數變動、可搜尋覆蓋與不小心引入重複資料。
- **考慮過的替代方案**:

  - 只改資料不改測試: 捨棄，會讓既有 count 基線與驗收證據失真。
