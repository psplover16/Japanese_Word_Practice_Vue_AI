## User Scenarios & Testing *(mandatory)*

### User Story 1 - 修正練習頁結果區操作與表格標示 (Priority: P1)

作為在字母練習頁反覆練習的使用者，我希望最近一次不熟題目結果區的清除操作與頁面內容標示更清楚，讓我能快速重置結果並避免多餘資訊干擾。

**Why this priority**: 這是使用者每次練習都會直接看到與操作的主流程，若文字、捲動與表格標示不符合預期，會立即影響基本使用體驗。

**Independent Test**: 在字母練習路由完成一次測驗產生最近一次結果後，可獨立驗證下方結果區按鈕文案、清除後的狀態、清除後的平滑捲動，以及兩個表格右側不再顯示多餘代號文字。

**Acceptance Scenarios**:

1. **Given** 使用者已在字母練習路由完成一次測驗並產生最近一次不熟結果，**When** 使用者點擊下方結果區的清除按鈕，**Then** 系統應清除最近一次不熟結果、更新畫面狀態，並將頁面平滑捲動回到該路由頂部。
2. **Given** 字母練習路由初次載入或重新整理，**When** 使用者查看清音表與濁音/半濁音表，**Then** 兩個表格右側都不應再顯示 `tableA` 或 `tableB` 文字，且畫面不出現額外空白佔位造成的錯位。
3. **Given** 最近一次不熟結果區有顯示清除按鈕，**When** 畫面寬度縮小到主要手機驗收尺寸，**Then** 按鈕文案應顯示為「清除」且不得斷行。

---

### User Story 2 - 提升測驗彈窗題目辨識度 (Priority: P2)

作為正在進行字母測驗的使用者，我希望彈窗內考試區塊最上方題目列的假名更醒目，讓我在手機與桌機上都能更快辨識題目內容。

**Why this priority**: 題目是測驗流程的核心內容；若字級過小，會直接降低辨識效率與答題流暢度，但不影響結果清除與資料正確性，因此排在第二優先。

**Independent Test**: 在字母練習路由選題並開啟測驗彈窗後，可獨立驗證考試區塊最上方題目列字級明顯大於現況，且題目、答案、提示與操作按鈕仍維持完整可見且不重疊。

**Acceptance Scenarios**:

1. **Given** 使用者在字母練習路由開啟測驗彈窗，**When** 題目顯示於彈窗中央考試區塊最上方的題目列，**Then** 題目假名字級應明顯放大至接近現況的 2.5 倍，並保持在卡片內可辨識且不裁切。
2. **Given** 使用者在主要手機驗收尺寸與桌機尺寸開啟測驗彈窗，**When** 檢視題目、答案、提示與底部按鈕區，**Then** 所有內容都應維持排版穩定，不可互相重疊或推出彈窗可視範圍。

---

### User Story 3 - 簡化並穩定 Pages 部署流程 (Priority: P3)

作為維護此專案的開發者，我希望 `dev` 與 `main` 的自動部署流程改用 GitHub 官方 Pages workflow，並避免舊內容殘留造成的部署錯誤，讓我能在保留 staging 與 production 可用性的前提下更直觀地維護交付流程。

**Why this priority**: 這會直接影響後續每次發版的可靠性與維護成本，但不會改變一般使用者當前的主要練習流程，因此排在第三優先。

**Independent Test**: 檢視 CI/CD 工作流程與專案文件，可獨立驗證 `dev` 與 `main` 的 Pages 發佈流程不再依賴自製推送腳本，且部署產物不會因殘留舊內容導致錯誤。

**Acceptance Scenarios**:

1. **Given** 維護者推送 `dev` 或 `main` 分支，**When** CD workflow 執行部署，**Then** 系統應使用 GitHub 官方 Pages Actions 流程完成對應環境的發佈，而不是依賴自製分支同步腳本。
2. **Given** 同一 repository 需要保留 staging 與 production 的可用部署結果，**When** 任一分支再次部署，**Then** 新的部署流程應處理舊內容殘留風險，避免因未清理或錯誤覆寫導致站點異常。
3. **Given** 維護者查看 repository 文件與架構說明，**When** 部署流程已完成調整，**Then** README 與架構文件應同步反映新的部署方式、必要設定與維護注意事項。

---

### Edge Cases

- 字母練習路由在沒有最近一次不熟結果時，不得顯示會誤導使用者的清除結果狀態或觸發多餘捲動。
- 若使用者在清除最近一次不熟結果後立即再次清除，系統應維持穩定，不得出現 runtime error、render failure 或 browser console error。
- 平滑捲動回頂部時，若使用者位於路由較高位置或頁面高度不足，系統仍應平順處理，不得出現負座標或跳動。
- 放大測驗彈窗題目字級後，題目為單一假名、較寬字形或不同字種時，都必須維持在彈窗卡片可視範圍內。
- 本功能僅限字母練習相關路由、其測驗彈窗與 CD/部署文件；文法、單字與其他未被明示的路由不得被引入相同變更。
- 若部署流程需要調整專案結構、workflow、部署文件或移除舊腳本，必須同步更新 `PROJECT_ARCHITECTURE.md`，且不得保留已失效的部署說明。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須將字母練習路由中最近一次不熟結果區的次要清除按鈕文案改為「清除」，且按鈕文字在主要手機驗收尺寸下不得斷行。
- **FR-002**: 系統必須讓最近一次不熟結果區的清除操作與上方工具列的清除最近結果使用相同的資料清除邏輯，以確保兩者清除的是同一份最近一次不熟結果資料。
- **FR-003**: 系統必須在使用者從最近一次不熟結果區完成清除後，將字母練習路由畫面平滑捲動回該路由頂部。
- **FR-004**: 系統必須移除字母練習路由清音表右側的 `tableA` 顯示文字，且不得以其他多餘代號取代。
- **FR-005**: 系統必須移除字母練習路由濁音/半濁音表右側的 `tableB` 顯示文字，且不得以其他多餘代號取代。
- **FR-006**: 系統必須放大測驗彈窗中央考試區塊最上方題目列的假名文字，使其視覺尺寸約為現況的 2.5 倍，同時保留答案區、提示區與操作按鈕的可見性。
- **FR-007**: 系統必須確保放大後的測驗彈窗在主要手機驗收尺寸、平板尺寸與桌機尺寸下都不出現裁切、重疊、水平溢出或無法辨識的內容。
- **FR-008**: 系統必須將 `dev` 與 `main` 的 Pages 發佈流程改為 GitHub 官方 Pages Actions 寫法，移除不再需要的自製部署腳本與相關依賴。
- **FR-009**: 系統必須讓新的 Pages 部署流程明確處理舊部署內容殘留風險，避免 `dev` 或 `main` 任一後續部署因先前產物殘留而導致站點錯誤或覆蓋異常。
- **FR-010**: 系統必須在新的部署流程完成後，同步更新 README、部署說明與 `PROJECT_ARCHITECTURE.md`，使維護者能從文件得知新的部署方式、環境對應與必要設定。
- **FR-011**: 本功能只可出現在字母練習相關路由、測驗彈窗與部署文件/工作流程；文法路由、單字路由與其他未指定介面不得出現本次新增的互動或版面變更。

### Key Entities *(include if feature involves data)*

- **最近一次不熟結果快照**: 代表字母練習最近一輪測驗中被標記為不熟的題目集合，包含清除時機、更新時間與結果列表。
- **測驗彈窗題目卡片**: 代表測驗流程中顯示題目、答案、提示與操作按鈕的視覺容器，需遵守不同裝置尺寸下的排版穩定性。
- **部署目標**: 代表由 `dev` 與 `main` 觸發的 staging 與 production 發佈結果，需定義環境對應、部署來源與舊內容處理策略。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者在字母練習路由完成一次測驗後，能在 5 秒內辨識並操作下方結果區的「清除」按鈕，且清除後 1 秒內看到結果區消失並回到頁面頂部。
- **SC-002**: 在 375px、768px 與 1024px 驗收尺寸下，字母練習路由與測驗彈窗的主要內容不出現水平捲動、文字重疊、按鈕裁切或無法辨識的題目。
- **SC-003**: 維護者在不手動管理額外部署分支內容的情況下，能從一次 `dev` push 與一次 `main` push 各自完成成功的 Pages 部署，且站點不因殘留舊內容產生異常。
- **SC-004**: README 與 `PROJECT_ARCHITECTURE.md` 的部署描述與實際 workflow 保持一致，維護者可在 10 分鐘內依文件完成部署設定確認。

## Assumptions

- 上方工具列的清除最近結果行為是目前正確的基準，下方結果區清除按鈕需對齊同一資料清除結果後再額外執行平滑捲動回頂部。
- 本次部署流程調整以保留 `dev` 對應 staging、`main` 對應 production 的雙環境可用性為前提。
- 若 GitHub 官方 Pages Actions 無法直接提供雙環境同時存在的自然映射，規格允許透過官方支援的部署配置重新設計承載方式，但不得退回維護成本較高且容易殘留舊內容的自製同步腳本。

## Repository Hygiene *(mandatory)*

- 確認 repository 已包含 `.gitignore`，且本次變更不得將 `node_modules/`、`build/`、`dist/`、`coverage/` 等可重建產物納入版本控制。
- 若部署流程調整導致 workflow、腳本、文件或結構發生變更，必須同步更新 `PROJECT_ARCHITECTURE.md`。
- 若移除舊部署腳本或舊說明文件，必須同步刪除或更新所有失效引用，避免倉庫中留下互相矛盾的維護資訊。
