# Feature Specification: 測試與自動交付基礎建設

**Feature Branch**: `002-testing-cicd-foundation`  
**Created**: 2026-03-25  
**Status**: Draft  
**Input**: User description: "導入 unit test + e2e + GitHub Actions CI/CD"

> 本規格以繁體中文（zh-TW）撰寫，聚焦在開發者工作流程、品質門檻與部署結果。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 建立可重複執行的測試基線 (Priority: P1)

作為專案開發者，我需要在本地與遠端都能用固定指令執行靜態檢查、單元測試、建置與基本使用流程驗證，讓我在修改程式後可以快速知道是否造成回歸。

**Why this priority**: 若沒有穩定的測試基線，後續所有 CI/CD 自動化都只是在包裝不可靠的流程，無法先建立可信的品質門檻。

**Independent Test**: 只完成這個故事時，開發者仍可用文件化指令在本地執行 lint、單元測試、建置與至少兩條端對端檢查，並得到明確成功或失敗結果。

**Acceptance Scenarios**:

1. **Given** 開發者已完成相依安裝，**When** 依文件執行本地測試與建置指令，**Then** 系統會依序完成靜態檢查、單元測試、建置與端對端檢查，並以非零結束碼表示失敗。
2. **Given** 核心純邏輯模組被修改，**When** 執行單元測試，**Then** 至少三個核心邏輯模組會被自動驗證，且失敗案例可指出回歸位置。
3. **Given** 應用程式可被啟動，**When** 執行端對端檢查，**Then** 至少一條 smoke 流程與一條核心使用流程會被驗證。

---

### User Story 2 - 在審查流程中自動阻擋回歸 (Priority: P2)

作為 pull request 的審查者，我需要在 push 與 pull request 階段自動看到檢查結果，確保未通過的程式碼無法被誤判為可合併。

**Why this priority**: 當本地測試存在後，下一步最有價值的是把它們放進審查入口，否則品質仍取決於開發者是否手動執行。

**Independent Test**: 只完成這個故事時，審查者可從平台 workflow 結果確認 lint、單元測試、建置與端對端檢查會在指定事件自動執行，且任何一項失敗都讓工作流失敗。

**Acceptance Scenarios**:

1. **Given** 開發者建立或更新 pull request，**When** 自動化檢查被觸發，**Then** 系統會自動執行安裝、靜態檢查、單元測試、建置與端對端檢查。
2. **Given** 任一檢查步驟失敗，**When** workflow 完成，**Then** 該次工作流狀態必須顯示失敗，不得被視為通過。
3. **Given** 端對端檢查失敗，**When** 審查者查看結果，**Then** 系統應保留足夠的失敗輸出或附件，讓審查者能追查問題。

---

### User Story 3 - 依分支自動部署到對應環境 (Priority: P3)

作為維護者，我需要在指定分支完成合併後自動部署，讓測試環境與正式環境都能以一致流程交付，並降低人工漏步的風險。

**Why this priority**: 自動部署能把前兩個故事建立的品質門檻延伸到交付流程，但前提是測試與 CI 已經可被信任，因此優先度排在第三。

**Independent Test**: 只完成這個故事時，維護者可在 `dev` 與 `main` 的推送後觀察到對應部署工作流觸發，並產生清楚的環境歸屬、乾淨的公開站點內容與部署結果。

**Acceptance Scenarios**:

1. **Given** 程式碼推送到 `dev` 分支，**When** 部署工作流執行成功，**Then** 測試環境會收到最新版本，且不得污染正式環境的公開內容。
2. **Given** 程式碼推送到 `main` 分支，**When** 部署工作流執行成功，**Then** 正式環境會收到最新版本，且公開站點不得再引用 `/src/` 原始碼路徑。
3. **Given** 公開站點根目錄曾殘留錯誤的原始 repo 內容，**When** 任一對應部署工作流再次執行，**Then** 系統必須清除不安全的殘留內容，避免站點繼續輸出錯誤入口頁。
4. **Given** 部署所需設定缺漏或權限不足，**When** 部署工作流執行，**Then** 系統必須明確失敗並指出缺失設定，而不是靜默略過。

---

### Edge Cases

- 當本地尚未安裝瀏覽器測試所需執行元件時，系統應提供可重複執行的初始化方式，而不是依賴口頭步驟。
- 當端對端檢查依賴啟動中的本地伺服器時，測試流程必須能自行啟動與關閉，而不是假設開發者已手動開站。
- 當專案沒有 `dev` 分支或尚未配置部署密鑰時，部署流程必須清楚說明如何建立或配置，而不是讓 workflow 成功但實際未部署。
- 當 `gh-pages` 首次建立或根目錄曾殘留原始 repo 檔案時，部署流程必須清出乾淨且安全的公開內容，而不是保留會引用 `/src/` 的入口頁。
- 當 smoke 流程可通過但核心使用流程失敗時，系統仍需將整體驗證視為失敗。
- 本功能僅涵蓋測試基礎設施、工作流與文件；現有業務功能內容與畫面設計不在本次調整範圍。
- 本功能新增的自動化規則只應作用於測試、建置、部署與文件路徑，不得改變現有畫面路由與使用者互動規格。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須提供一組文件化的本地指令，讓開發者可執行靜態檢查、單元測試、建置與端對端檢查。
- **FR-002**: 系統必須至少為三個核心純邏輯模組或函式建立單元測試，且測試結果可在本地與自動化流程中重複取得。
- **FR-003**: 系統必須至少提供兩條端對端檢查：一條驗證應用程式可成功啟動與進入主要入口，一條驗證核心使用流程可完成並產生可觀察結果。
- **FR-004**: 系統必須在 `pull_request` 與指定分支的 `push` 事件中自動執行安裝、靜態檢查、單元測試、建置與端對端檢查。
- **FR-005**: 任一自動化檢查失敗時，對應的工作流必須標示為失敗，不得繼續被視為可合併或可部署。
- **FR-006**: 系統必須保留足夠的失敗診斷資訊，讓維護者可追查端對端檢查或部署失敗原因。
- **FR-007**: 系統必須依分支自動部署到對應環境，其中 `dev` 對應測試環境、`main` 對應正式環境，且兩者的公開內容不得互相污染。
- **FR-008**: 系統必須在部署時只發布可公開執行的靜態網站內容，不得把原始 repo 檔案或會引用 `/src/` 的入口頁部署到公開站點。
- **FR-009**: 系統必須在部署設定缺漏、認證失效、公開內容不安全或環境保護條件未滿足時明確失敗，並指示需要補充的設定。
- **FR-010**: 系統必須補充專案文件，說明本地測試指令、自動化檢查內容、部署觸發方式與常見失敗排查。
- **FR-011**: 本功能的變更範圍必須限制在測試、建置、CI/CD 工作流、部署腳本與文件，不得引入與需求無關的功能性重構。

### Key Entities *(include if feature involves data)*

- **Validation Command Set**: 開發者在本地或自動化流程中執行的一組標準指令，包含靜態檢查、單元測試、建置與端對端檢查。
- **Pipeline Run**: 一次由 push、pull request 或部署事件觸發的工作流執行結果，具有成功/失敗狀態與診斷輸出。
- **Deployment Environment**: 由分支對應到的交付目標，至少包含測試環境與正式環境，並具備可追蹤的部署結果。
- **Test Scenario**: 用來驗證單元邏輯或使用者流程的自動化案例，需對應到明確的驗收價值。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新加入的開發者在完成相依安裝後，可於 10 分鐘內依文件成功執行本地驗證流程，且不需要額外口頭說明。
- **SC-002**: 每次 `pull_request` 驗證都會自動執行完整檢查流程，並在任一步驟失敗時於同一次工作流中明確標示失敗。
- **SC-003**: 維護者可在一次推送到 `dev` 與一次推送到 `main` 後，分別觀察到對應環境的自動部署紀錄，且公開站點不再出現 `/src/app/main.ts` 404。
- **SC-004**: 專案至少具備三個核心邏輯單元測試案例與兩個端對端驗證案例，且它們可在本地與自動化流程中重複執行。

## Assumptions

- 專案仍以現有前端應用為主體，本次不引入新的後端服務。
- 自動部署的實際承載平台可依專案現況選擇，但必須支援測試環境與正式環境兩種可區分的交付結果。
- 若正式環境需要人工核准，該核准可由平台環境保護規則提供，而不必由應用程式自行實作。

## Repository Hygiene *(mandatory)*

- 實作前必須確認 repository 已包含 `.gitignore`。
- 不得提交 `node_modules/`、建置輸出與測試暫存產物。
- 測試報表、瀏覽器快照與部署產物若屬可重建資料，應以 artifact 或忽略規則處理，不直接提交到版本庫。
