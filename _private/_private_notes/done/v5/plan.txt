Implementation Plan
Feature:
將目前專案 `變化規則` route 的主要內容，重寫為與
`https://psplover16.github.io/Japanese_Word_Practice_Vue/change-rules`
一致的高保真 table 版面。

==================================================
一、技術目標
==================================================

本次計畫的核心不是單純「顯示相同文案」，
而是讓目前專案在同一個 route shell 下，
重現參考頁主內容的：

1. section 順序
2. table 結構
3. table 樣式
4. 儲存格內容
5. 排版與換行規則

==================================================
二、架構原則
==================================================

原則 1
保留現有 route shell，不新增 route，不改 route tabs，不改 route title。

原則 2
主內容資料來源獨立化，避免和其他 route 共用不相干的 view 狀態。

原則 3
資料模型應允許表格高保真呈現，不為了抽象化而犧牲 rowspan / colspan / tfoot / nested list。

原則 4
驗收要同時覆蓋 DOM 結構與視覺表現，不能只驗文字。

==================================================
三、實作策略
==================================================

建議採用「受控 reference-table schema + route-specific renderer」策略。

1. route 層
   - 繼續使用現有 `GrammarView.vue`
   - 只替換其主內容來源與 rendering

2. data 層
   - 將 12 個容器整理為獨立 section records
   - 每個 section 至少包含：
     - id
     - title
     - subtitle
     - defaultExpanded
     - contentBlocks

3. block 層
   - 以 `referenceTable` 作為主要 block 類型
   - block 至少包含：
     - id
     - type
     - headerHtml 或等效 header metadata
     - bodyHtml
     - footHtml

4. renderer 層
   - `GrammarRulesRenderer.vue` 專責呈現受控 table 結構
   - `GrammarRulesSection.vue` 專責容器 header / subtitle / accordion
   - 樣式集中在 route-specific CSS，避免污染其他 route

==================================================
四、資料模型規劃
==================================================

推薦資料模型採「可維護的低抽象高保真」：

Section
1. `id`
2. `title`
3. `subtitle`
4. `defaultExpanded`
5. `contentBlocks`

ReferenceTableBlock
1. `id`
2. `type: referenceTable`
3. `headerHtml`
4. `bodyHtml`
5. `footHtml`

這種模式的原因：
1. 可保留 rowspan / colspan / tfoot
2. 可保留清單、範例、手動斷行
3. 可精準對應參考頁 DOM
4. 仍可用 section / block 做 CRUD

==================================================
五、內容檢查與建模策略
==================================================

每個容器都要做兩步驟：

Step 1
先建立 container audit baseline：
1. title
2. subtitle
3. table count
4. thead/tbody/tfoot 結構
5. row count
6. merged cell 規則
7. nested list 規則
8. 特殊高亮 cell

Step 2
將 baseline 落到本地資料檔與測試中。

這樣後續 CRUD 時，可以先定位：
1. 是哪個容器
2. 是哪個 block
3. 是哪種差異
4. 需要重跑哪類驗收

==================================================
六、樣式對齊策略
==================================================

因本次需求明確要求與參考頁一致，
所以樣式計畫必須逐類對齊：

1. Table shell
   - border-collapse / border-separate
   - table width
   - overflow behavior

2. Header cells
   - background color
   - font weight
   - text alignment
   - nowrap / wrap

3. Body cells
   - background color
   - text color
   - line-height
   - vertical alignment
   - nested content spacing

4. Footer cells
   - footer background
   - emphasis text
   - paragraph stacking

5. Special highlight cells
   - 保留參考頁中的深色 / 反白樣式

6. Subtitle rendering
   - 保留多行副標題
   - 不可被 truncate

==================================================
七、換行與對齊策略
==================================================

這次需要特別處理的不是只有表格有沒有出現，
而是每格內容的閱讀方式。

必須明確規劃：

1. 何處使用 `whitespace-pre-line`
2. 何處使用 `whitespace-pre-wrap`
3. 何處需要 `text-nowrap`
4. 何處需要 `break-words`
5. 何處是左對齊多行堆疊
6. 何處是置中單行表頭

本計畫中的 typography 驗收，明確包含「字級與粗細」，
不得只驗文字存在與否。

==================================================
八、容器逐項驗收設計
==================================================

每個容器都必須產出相同格式的 acceptance 檢查點：

Acceptance Group A: 結構
1. 是否與參考頁容器標題一致
2. 是否與參考頁副標題一致
3. table 結構是否一致
4. tr / td / th 是否一致
5. colspan / rowspan 是否一致

Acceptance Group B: 內容
1. 每格文字是否一致
2. 範例是否一致
3. 表尾是否一致

Acceptance Group C: 視覺
1. 換行是否一致
2. 對齊是否一致
3. 背景色是否一致
4. 字色是否一致
5. 字級是否一致
6. 粗細是否一致

==================================================
九、測試策略
==================================================

需要同時覆蓋 4 層測試。

1. Unit test
   - section ids、順序、容器數量
   - 特定容器標題與副標題
   - 重要關鍵字是否存在

2. Component test
   - accordion 展開/收合
   - renderer 可正確渲染 referenceTable
   - subtitle 多行保留
   - 含 tfoot 的 block 可渲染

3. DOM structure assertions
   - 關鍵容器的 row/col span 與內容存在
   - 關鍵 class 或 data-testid 存在

4. E2E / layout smoke
   - `/grammar` 可正常開啟
   - 12 個容器都存在
   - 關鍵容器展開後內容存在
   - mobile width 下無非預期 overflow

==================================================
十、詳細驗收清單設計
==================================================

計畫中應建立一份「逐容器驗收矩陣」的概念，至少覆蓋：

1. 語法系統差異
   - 三欄比較表
   - 表頭背景色
   - 範例字色與縮排

2. 各活用型意義
   - 單欄序號清單
   - 編號與文字的排列

3. 動詞型態分辨
   - 編號條列
   - 特例動詞分行呈現

4. 五段動詞表
   - rowspan 合併
   - 特殊高亮 cell
   - tfoot 派生列

5. 音便
   - 獨立容器，不可再併回五段動詞表
   - footer 說明列

6. 一段動詞
   - 與參考頁相同的 conjugation table

7. サ變動詞
   - 與參考頁相同的 conjugation table

8. カ變動詞
   - 標題與副標題分行
   - 表格結構一致

9. い形容詞
   - 表格結構與標題一致

10. ない形容詞
   - 表格結構與標題一致

11. だ助動詞
   - 多行副標題
   - 表格結構一致

12. 詞性變化規則
   - 巢狀清單層級
   - 粗體範例標頭
   - 清單縮排與排列方向

==================================================
十一、風險與對應
==================================================

風險 1
只靠手動轉寫容易遺漏文字或錯放 row/col span。

對應
建立逐容器檢查基準，必要時以瀏覽器實際渲染結果反查。

風險 2
使用過度抽象 schema 會破壞表格 fidelity。

對應
允許 reference-table 以較接近 HTML 的方式保存。

風險 3
只驗單元測試會漏掉視覺差異。

對應
補 component 與 e2e 驗收。
