# Feature: 導入 unit test + e2e + GitHub Actions CI/CD

## Background
目前專案已採用 Spec-Driven Development / GitHub Spec Kit 進行需求與開發流程管理，但尚未完整建立測試與自動化交付機制。  
為降低 AI 輔助開發造成的回歸風險，並提升 pull request / merge 階段的品質控管，需要導入以下能力：

- unit test
- e2e test
- GitHub Actions CI
- GitHub Actions CD

## Problem
目前專案存在以下問題：

1. 缺少可自動執行的小範圍邏輯驗證機制，核心函式或商業規則修改後容易產生回歸問題。
2. 缺少可驗證完整使用流程的 e2e 測試，頁面可編譯不代表功能可正常操作。
3. 缺少 pull request / push 階段的自動化檢查，測試與建置依賴人工執行。
4. 缺少 merge 後的自動部署流程，交付步驟不一致且容易遺漏。

## Goals
本需求目標如下：

1. 導入適合目前專案技術棧的 unit test 基礎架構。
2. 導入 Playwright e2e 基礎架構。
3. 在 GitHub Actions 建立 CI workflow，自動執行 lint、unit test、build、e2e。
4. 在 GitHub Actions 建立 CD workflow，依指定分支自動部署到對應環境。
5. 建立最小可用、可逐步擴充的 testing 與 delivery foundation。
6. 讓 AI 後續可依 Spec Kit 規格持續補測試，而非手動零散維護。

## Non-Goals
本階段不包含以下內容：

1. 不追求全面測試覆蓋率。
2. 不要求所有頁面立即具備 e2e。
3. 不重構整個專案架構，只在必要範圍內補足測試與 workflow。
4. 不要求首版即支援所有瀏覽器矩陣與所有部署環境。

## Functional Requirements

### FR-1 Unit Test Foundation
系統必須建立 unit test 基礎架構，並能於本地與 CI 執行。

### FR-2 Initial Unit Test Coverage
系統必須至少為 3 個核心純邏輯模組或函式建立 unit test。

### FR-3 E2E Foundation
系統必須建立 Playwright e2e 基礎架構，並能於本地與 CI 執行。

### FR-4 Initial E2E Coverage
系統必須至少提供：
1. 1 條 smoke test（例如首頁可正常開啟）
2. 1 條核心主流程測試（例如查詢、登入、建立資料、送出表單等）

### FR-5 CI Workflow
系統必須在 pull request 與 push 時自動執行：
- install
- lint
- unit test
- build
- e2e test

### FR-6 CI Failure Behavior
任一檢查失敗時，workflow 必須失敗，且不得視為通過。

### FR-7 CD Workflow
系統必須依指定分支自動部署：
- dev 分支 → staging / test environment
- main 分支 → production environment
  （若實際分支策略不同，依專案現況調整）

### FR-8 Documentation
系統必須補充 README 或 docs，說明：
- 本地如何執行 unit test
- 本地如何執行 e2e
- GitHub Actions CI/CD 的觸發方式
- 常見失敗排查方式

## Acceptance Criteria

1. 開發者可在本地成功執行 unit test。
2. 開發者可在本地成功執行 e2e。
3. pull request 時，GitHub Actions 自動執行 lint、unit test、build、e2e。
4. 任一測試或建置失敗時，CI 明確失敗。
5. 合併到指定分支後，CD 會自動部署到對應環境。
6. 專案文件已補上測試與 CI/CD 說明。
