本文件用來把本次需求收斂成可執行、可驗收、可回歸驗證的版本。

==================================================
一、最終需求解讀
==================================================

本次真正需求不是：
1. 新增一個新的 `/change-rules` route
2. 做一個長得差不多的文法頁
3. 只搬文字內容

本次真正需求是：
把參考頁
`https://psplover16.github.io/Japanese_Word_Practice_Vue/change-rules`
中「最上方 route title 與 route 切換按鈕以下」的主要內容，
以高保真方式重寫到目前專案既有的 `變化規則` route 主內容內。

==================================================
二、明確保留項
==================================================

以下內容不應改動：

1. 目前專案既有 route path
2. 目前專案既有 route title
3. 目前專案既有 route tabs / 路由切換按鈕
4. 目前專案既有 app shell 與外層布局責任

==================================================
三、明確替換項
==================================================

以下內容應視為替換標的：

1. 目前專案 `變化規則` route 內的舊主內容
2. 舊主內容中任何簡化版的規則卡片、簡化表格、摘要文字
3. 與參考頁內容不一致的文字、結構、換行、色彩、對齊、字級

==================================================
四、比對基準的優先順序
==================================================

Priority 1
參考頁在瀏覽器中實際呈現的 DOM / 視覺排版結果

Priority 2
目前專案既有 route shell 的殼層一致性

Priority 3
目前專案既有色票或樣式習慣

也就是說，若目前專案既有色票與參考頁內容衝突，
應優先以參考頁主內容的視覺結果為準，
而不是為了沿用現有配色而改變表格視覺層次。

==================================================
五、最新需求對舊需求的覆蓋
==================================================

先前曾有「配色可以依照目前專案配色」的寬鬆表述。
本次新需求已明確提高要求，包含：

1. 文字顏色
2. td / tr 背景色
3. 對齊方式
4. 字級與粗細
5. 是否允許斷行

因此，本次應視為：
「排版與 table 細節以參考頁一致為優先」
這個要求覆蓋掉先前較寬鬆的表述。

==================================================
六、需要達成的保真等級
==================================================

本次要求的保真等級定義如下：

Level A 內容保真
1. 每個容器標題逐字一致
2. 每個副標題逐字一致
3. 每個 table 內所有文字逐字一致
4. 所有範例、註記、表尾補充逐字一致

Level B 結構保真
1. 容器數量一致
2. 容器順序一致
3. table 數量一致
4. tr / td / th 順序一致
5. colspan / rowspan 一致
6. 巢狀清單與表尾一致

Level C 視覺保真
1. 換行行為一致
2. 對齊方式一致
3. 背景色層級一致
4. 文字色層級一致
5. 字級與粗細一致

==================================================
七、驗收方法的明確化
==================================================

本次驗收不能只靠「肉眼大致看起來像」。
必須至少包含以下三層驗收：

第一層：資料與文字驗收
1. section 清單與順序
2. 容器標題與副標題
3. 每個儲存格文字

第二層：DOM 結構驗收
1. tr / td / th 數量
2. colspan / rowspan
3. thead / tbody / tfoot
4. 巢狀清單

第三層：視覺與排版驗收
1. 換行
2. 對齊
3. 顏色
4. 字級
5. 粗細
6. 手機寬度下的呈現

==================================================
八、每個容器都要做的驗收面向
==================================================

對每個容器都必須做下列驗收：

1. Header audit
   - title
   - subtitle
   - header cell 樣式

2. Structure audit
   - row count
   - column count
   - merged cell 規則
   - list / note / footer 結構

3. Content audit
   - 每格文字
   - 範例文字
   - 表尾說明

4. Wrapping audit
   - nowrap / wrap / pre-wrap
   - 手動斷行
   - 多行堆疊

5. Visual audit
   - text color
   - background color
   - border
   - highlight cell

6. Typography audit
   - font size
   - font weight
   - emphasis text

==================================================
九、明確列出需完整比對的容器
==================================================

以下 12 個容器全部都必須逐一驗收，不可抽樣：

1. 語法系統差異
2. 各活用型意義
3. 動詞型態分辨: 一段/五段/不規則
4. 五段動詞表(詞尾母音變化)
5. 音便 (詞尾接尾一起改變)
6. 一段動詞 (辭書型 結尾必定是 る)
7. サ變動詞 (する動詞為結尾的動詞)
8. カ變動詞 (只有来る)
9. い形容詞
10. ない形容詞
11. だ助動詞
12. 詞性變化規則

==================================================
十、對 CRUD 的具體要求
==================================================

雖然本次目標是高保真重寫，但後續仍需方便維護。
因此規格上明確要求：

1. 能辨識每個容器的獨立資料來源
2. 能辨識每個 table 區塊的獨立責任
3. 能在不誤傷其他容器的前提下，修改特定容器內容
4. 能在不整頁重寫的前提下，做單容器 CRUD
5. 能在修改單一 table 後，重新執行對應驗收

==================================================
十一、風險澄清
==================================================

風險 1
若使用過度抽象的資料模型，容易無法保留 rowspan / colspan / tfoot / 巢狀清單。

結論
資料模型可以比先前更貼近 HTML table 結構，只要仍可定位各容器與各 table 區塊，即可接受。

風險 2
若只驗文字，不驗排版，仍可能與參考頁差很多。

結論
必須把「排版驗收」提升為一級需求，不得只驗 content。

風險 3
若只驗桌機，不驗手機，會漏掉換行與 overflow 問題。

結論
必須補 mobile width 驗收。

==================================================
十二、最終澄清結論
==================================================

1. 主內容以參考頁為唯一對照基準。
2. route shell 保留不動。
3. 舊主內容完全廢棄。
4. 12 個容器全部逐一驗收。
5. 驗收必須覆蓋：
   - 結構
   - 文字
   - 換行
   - 顏色
   - 對齊
   - 字體樣式
6. 驗收結果必須詳細到足以支援後續 CRUD 與 regression。
